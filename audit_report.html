Fix first

the ones worth stopping for
Critical
mobile/src/store/userStore.ts:9-23 — getDeviceId()

Every real device shares one hardcoded profile ID

The device-ID generator checks window.localStorage to decide whether it can mint a real per-install ID — that global doesn't exist in React Native, so on every Android/iOS device the check fails and the function falls through to a single hardcoded string, device_seasarathi_default_01. Every fisherman who installs the app writes their vessel type, home port, and language to the same backend profile record, overwriting whoever set it last. This has presumably been true since the profile feature shipped.

Fix: generate a real UUID with expo-crypto or similar, persist it via AsyncStorage (already a dependency, used in offlineService.ts) on first launch, and use that. Web can keep the localStorage path as a fallback.

High
backend/requirements.txt

Five imported packages are missing from requirements.txt

copernicusmarine, openmeteo_requests, requests_cache, retry_requests, xarray are all imported by weather_service.py / the Copernicus grid fetch, but absent from the file. The app only works today because they happen to already be installed in this dev venv — a clean checkout (a teammate, CI, a redeploy) breaks on the first weather or grid call.

Fix: pip freeze the current venv and reconcile requirements.txt against it.

High
mobile/src/services/voiceService.ts:23-37 — playOneClip()

One bad TTS clip permanently disables the speaker button on every message

Playback only resolves on a didJustFinish event — there's no error listener and no timeout. If a WAV clip ever fails to decode on a given device, that promise never settles. Because ChatScreen gates the speak button on a single shared speakingMessageId !== null, one stuck clip locks the button for every message, not just the one that failed, with no visible error and no way to recover short of restarting the app.

Fix: add an error/status listener (or race against a timeout) that also resolves the promise, so the caller's try/catch and its finally can actually clear the stuck state.

High
mobile/src/screens/MapScreen.tsx:432-433

The vessel marker on the map shows fabricated speed and heading

The "MY VESSEL" marker's description is a fixed literal — "8.4 KTS • 285° WNW" — displayed as if it were live telemetry, for every port, every time, regardless of whether the boat is even moving. This is exactly the class of fabricated-data-shown-as-real issue that was deliberately scrubbed from PFZScreen/AlertsScreen/IndiaMapCanvas earlier — missed here.

Fix: drop the fabricated numbers; show only what's real (vessel name/port), or omit the description entirely until real GPS speed/heading is wired up.

Backend

main.py · src/services · src/agents · src/utils

Bugs

High
src/services/risk_heatmap.py:18-19, 71-73

Risk heatmap cache isn't keyed by resolution

The module-level cache stores one result regardless of the requested resolution_deg. A call at 0.25° within 30 minutes of a prior 1.0° call silently returns the wrong-resolution grid.

Fix: key the cache dict by resolution_deg.

High
src/services/copernicus_service.py:37-94

Nearest-point lookup is an unindexed O(n) scan over 30,398 grid points, run synchronously

lookup_nearest()/find_within_radius() do a linear haversine scan on every call, with no spatial index, inside an async def handler — no asyncio.to_thread. /pfz/nearest calls this up to 5× per request (~150K haversine computations), blocking the event loop for every other concurrent request meanwhile.

Fix: build a scipy.spatial.cKDTree once inside _load_grid()'s existing lru_cache, and wrap the handler body in asyncio.to_thread.

Security

Medium
main.py:55-72

CORS allows every origin with credentials enabled

Self-flagged in a comment ("hackathon dev — restrict in prod"), but with zero authentication anywhere in the API, any web origin can currently make credentialed requests to every endpoint.

Fix: restrict allow_origins before any real deployment.

Medium
main.py:227-267 — POST/DELETE /profile

Profile write/delete has no ownership check

Anyone who knows or intercepts a device_id can overwrite or delete that profile — no auth on a state-mutating endpoint.

Fix: at minimum, pair with a real per-device ID (see the userStore bug above) and consider a lightweight device token.

Medium
main.py:658-676 — POST /voice/tts

No length cap on TTS request text

A large payload silently fans out into many sequential Sarvam API calls (see the chunking in sarvam_client.py) with no upper bound — a cost/quota exposure with no client-side reason to ever send that much text.

Fix: reject (422) text over a sane limit, e.g. 5–10K characters, before chunking.

Efficiency

Medium
main.py — /geojson/pfz, /geojson/boundaries, /landing/nearest

Static GeoJSON re-read and re-parsed from disk on every request

These files never change at runtime, yet are json.load'd synchronously inside the handler every single call — the same codebase already has the right pattern one file over (copernicus_service._load_grid's lru_cache), just not applied here.

Fix: wrap a _load_geojson(path) helper in @lru_cache.

Medium-High
main.py:432-522 — GET /alerts

Synchronous weather fetch blocks the event loop

weather_service.fetch_combined_forecasts_for_grid uses a synchronous openmeteo_requests client (retry-wrapped, up to 5 retries with backoff) directly inside the async handler — network I/O blocking is worse than the disk-I/O case above.

Fix: wrap in asyncio.to_thread, same as the freshness refresh path already does elsewhere.

Services & state

services · store · utils · constants · map components

Bugs

Medium
userStore.ts (whole store)

No persistence, and the backend profile only ever loads from one screen

Vessel type, risk tolerance, port, role and language are plain in-memory Zustand state — nothing survives a cold start except by re-fetching, and loadFromBackend() is only ever called from ProfileScreen's own effect, not at app root. A cold start landing on any other tab runs on hardcoded defaults (English, Kochi) until Profile is visited. Compounds the device-ID bug above.

Fix: wrap the store in Zustand's persist middleware with an AsyncStorage adapter, and/or call loadFromBackend() once at root mount.

Medium
mapCacheDb.ts:143-146

One bad PFZ row rolls back the entire offline-cache save

PFZ row id is String(props.UID ?? i) — a duplicate/missing UID in the source GeoJSON throws a primary-key violation inside the transaction, which rolls back PFZ + boundaries + landing centers together. No partial-success path; the whole cache silently fails to save.

Fix: use INSERT OR REPLACE, matching the pattern already used for map_cache_meta.

Low
mapCacheDb.ts — landing_centers

Same collision class as above

props.LC_UNIQUE_ ?? i — same fragility if that property is ever null/duplicated.

Fix: same as above.

API layer & hygiene

Medium
components/GoogleMapContainer.tsx:33-34

A live Google Maps API key is hardcoded as a source fallback

Even with no restrictions on that key today, a real credential checked into version control can't be rotated without a code change and is now permanently in git history.

Fix: drop the fallback; fail into the existing "Could not load Google Maps" error state if the env var is unset.

Medium
MapScreen.tsx:159-166 — nearestRiskFeatures

Risk-marker list recomputed and reallocated on every render

Unlike pfzFeatures/boundaryFeatures (already memoized), this sort+slice runs fresh every render — new array/object references cascade into needless re-renders of every native risk Circle, the web overlay-redraw effect, and the Static-Maps image URL/reload. Same category as the drag-lag bug fixed earlier this session, on a different array.

Fix: wrap in useMemo keyed on [riskData, portInfo.latitude, portInfo.longitude].

Low
api.ts — voiceAPI.tts

Client TTS timeout (30s) can be tighter than the backend's own worst case

Long advisories get chunked into multiple sequential Sarvam calls server-side; a long enough response could exceed 30s server-side before the client's own timeout fires, surfacing as a silent "nothing happened."

Fix: raise the client timeout to ~60s, or cap total server-side chunks.

Low
IndiaMapCanvas.tsx:123-132, 186-193

Vector-canvas geometry unmemoized; one fake decorative curve remains

pfzLines/boundaryLines re-run geometryToSegments+projectCoord every render of "India Map" mode. Separately, the "Bathymetry Isobaths" path is still a fixed hand-drawn curve rendered unconditionally regardless of real depth data — same category as the PFZ-polygon fabrication fixed elsewhere in this file, missed in that pass, and its layer toggle was already removed so it can't even be hidden.

Fix: memoize the geometry; remove the fake bathymetry curve (same call made for the fake "Wind Flow Streamlines" toggle earlier) or replace it with real data.

hostUri.split(':')[0] would return [ for an IPv6 literal host. Unlikely in practice (Expo dev hosts are normally IPv4 LAN).
